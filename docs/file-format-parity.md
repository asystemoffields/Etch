# File-format parity with Microsoft Word

Every format Word opens or saves, what Etch does with it, and how it's tested. Fidelity is the
share of a typical real-world file's content and formatting that survives (read: shows correctly;
write: Word opens it showing the same). Summary in [`target-app-parity.md`](target-app-parity.md);
the work items are in [`gaps.md`](gaps.md).

**Dimension: ~60% (estimated).** The weighted table
gives ~64%; we discount it to ~60% because DOCX fidelity has never been checked on real-world
files. DOCX dominates the weight: a Word user sends and receives .docx; everything else is
occasional.

## Legacy DOC/DOT document properties

The binary Word reader imports SummaryInformation text properties: title, subject, author,
keywords, description, last editor and revision. Code-page strings use their declared
Windows single-byte encoding, UTF-8 or UTF-16LE; UnicodeString lengths are counted in UTF-16
units. Metadata streams are capped at 2 MiB and individual values at 64 KiB. Invalid optional
metadata is skipped without losing the document body. Creation/modification timestamps and
DocumentSummaryInformation/custom properties are not imported by this change; DOC/DOT
remain read-only formats and encrypted legacy documents remain unsupported.

Tests create OLE property sets in Rust and exercise the public document reader for normal
DOCs, templates, accented/Cyrillic/Unicode properties and malformed lengths/offsets. A local
LibreOffice-generated DOC and DOT containing an original synthetic document reproduced the
missing-title bug before this change and retain their title after it.

## Paragraph-default preservation
The styles reader records whether `w:pPrDefault` exists. The writer keeps an omitted
container omitted when its modeled properties are still empty. An explicitly empty
container stays present, and editing document-default spacing writes the new values.
New documents and older serialized style sheets keep their explicit defaults.
`crates/docx/tests/fixtures.rs` covers omitted `docDefaults`, omitted paragraph defaults,
empty containers and populated defaults across two save/reopen cycles. This preserves
application-defined defaults without assigning inferred Word spacing values to the model.
Observed in Word for Mac 16.113.3 (26092714): three synthetic paragraph-default
controls (omitted, explicitly empty, populated) and two reduced invoice controls retain
identical text, glyph/image geometry, page sizes and embedded font-program hashes through
two Etch save/reopen cycles. All fifteen variants open without repair warnings.
Word PDFs and measurements remain local under ignored `plan/word/`; they are not fixtures.
These checks cover preservation on Word reopen, not Etch pagination parity.
The [public OOXML reference](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.paragraphpropertiesdefault?view=openxml-3.0.1)
describes omission as leaving paragraph defaults application-defined. Real-world corpus
coverage and Etch layout matching remain separate gaps.
## Custom XML store preservation
A reduced original bound-control DOCX loses its backing data, item properties and relationship
on main, both without editing and after unrelated edits. Main's content-control support
preserves control metadata, including binding attributes, while this custom XML path keeps the
backing store through the bounded opaque part graph: payload bytes, content types and
related-part IDs survive two edited save/reopen cycles.
The public [dataBinding contract](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.databinding?view=openxml-3.0.1)
maps a control to a custom XML data part; its [item properties](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.customxmldataproperties.datastoreitem?view=openxml-3.0.1)
identify the store. Keeping displayed text alone does not preserve that mapping. This change
preserves stores without evaluating XPath or synchronizing control edits into XML.
Focused original tests cover package/main roots, multiple/shared stores, cycles, external schema
references, missing parts, UTF-16 payloads, strict relationship types and reserved filenames.
The bibliography names used by are reserved; bibliography already loaded into the source
model belongs to its writer. Word-derived files are not fixtures. No readiness estimate rises
from these synthetic package checks, and native Word rendering/binding behavior remains untested.
## Native save-path guarantees
Native `io::save_path_with` serializes (and, for password-protected DOCX, encrypts) before creating an exclusively owned sibling temporary file. It writes and synchronizes that file, closes it, then replaces the destination. Failed preparation or replacement keeps the original bytes; cleanup removes only the save's temporary file, on a best-effort basis. Existing `<name>.tmp` files, directories and links are untouched. A new document gets the default mode (`0666` less the umask). When replacing an existing regular file, the Unix temporary file starts with mode `0600` and then takes the existing file's basic permissions. Serialization and format support are unchanged. Native `io::write_file` (Print to PDF, `file.printPdf`; Export Page as PNG, `file.exportPng`) writes through the same path. If the folder refuses the temporary file with a permission error (macOS privacy protection, a read-only folder), an existing destination is never written in place: it stays byte for byte as it was, and the error says to use Save As to another folder or to give Etch access to the folder (on macOS, System Settings › Privacy & Security › Files and Folders). Only a destination that doesn't exist yet is created directly (exclusively, so nothing already there is opened); a failed direct write removes it again. Unit tests cover a read-only folder on Unix; the macOS privacy case is not yet confirmed on a Mac.
A save through a symbolic link (or a chain of them) writes the file at its end: the temporary file is made beside that file and renamed over it, so the link stays a link; the automation write root is checked against that file. A read-only destination is refused, as Word does, with an error that suggests Save As (Save, AutoSave and exports alike; the desktop shows it in the refused-save dialog, which offers Save copy…). A folder, a device or anything else that isn't a regular file is refused with a plain error saying so (it used to be reported as "changed by someone else" when the session had a file). A replaced file keeps its mode and, on Linux and macOS, its extended attributes (on Linux these carry POSIX ACLs, so they are kept too); its owner and group are kept where the user may set them (root, or a group the user belongs to) and are otherwise the user's own. Not kept: macOS ACLs, Windows security descriptors (the replacement takes its folder's inherited ACL) and creation times.
Synthetic CLI cases and `engine/tests/safe_save.rs` cover occupied names, links, blocked replacement, missing directories, Save As session state, password-protected saves and original-file protection on macOS. Unit tests inject preparation errors and interleave two prepared saves. Independent saves use separate files; the last successful replacement wins. Session-owned Save and AutoSave also apply the content check described below.
After the rename the containing folder is synchronized (Unix), so the new name survives a power loss: a save reported as done is on disk. On macOS the standard library's `sync_all` is already `fcntl(F_FULLFSYNC)`, which flushes the drive's cache too. A folder that can't be synchronized (`EINVAL`/unsupported on some network and FUSE mounts) doesn't fail the save; any other folder-sync error is logged, as the file is already in place. The order (sync file, rename, sync folder) is pinned by a unit test through a test-only trace. Windows runtime behavior, macOS extended attributes, real disk-full conditions, power loss and network filesystems are not verified by these tests. Cleanup can fail when storage or permissions change, and process termination can leave a temporary file. No Word observation was needed for this filesystem change; it makes no new format-fidelity claim.

## Native save protection

Native `file.open` records a SHA-256 content identity from the same bytes parsed. Save compares
current bytes after preparing an owned sibling replacement. Changed, missing or unreadable
owned destinations return a typed conflict, retaining local edits, dirty state, password, path
and save metadata. Successful saves advance the expected identity. Identical-byte replacement
is benign; Save As to another file remains available, while path spellings, symlinks and hard
links to the open file retain its protection. Identity belongs to each Session, is reset on
new/open/recovery and is not serialized in the document. Password-protected files are compared
as ciphertext; hashing creates no plaintext file.

Versioned opens and saves also enforce the automation read and write roots. A refused open
keeps the current document; a refused save keeps the original bytes, local edits and metadata.
Write-only access to a separate output folder still permits Save As there.

These checks run on open/save, not typing or dirty-state polling: nothing watches the file,
so an idle window does no work for them. AutoSave, which writes on a worker thread, applies the
same check there and records the version it wrote; on a conflict it stops and offers Save copy….
The open reuses the one capped, regular-files-only read every open goes through. Any save over
the session's own file advances the expected version, a plain-text save over the `.txt` it
opened included. A file whose length differs is refused without being read; otherwise the save
reads and hashes it. Cost, measured on Linux (Ryzen 5 7530U, SHA-256 in hardware, synthetic
27 MB DOCX): ~31 ms per hash, so one on open and two per save (the file on disk and the bytes
written); a 5 MB document stays under ~6 ms each. On a network share each save re-reads the
file over the network. Browser-hosted bytes and standalone `io::save_path_with` exports have
no native Session baseline, nor has a file the app opened by a name that isn't valid Unicode
(read through `file.open`'s `data`). Save As to an unrelated existing file retains its explicit
replacement behavior. There is a check-to-rename race, so this does not establish atomic
multi-writer safety or network-filesystem locking. Runtime tests use synthetic documents on macOS and Linux; Windows
runtime remains unqualified.

## What decides beta for formats

1. A **real-world DOCX corpus** opened, rendered and round-tripped, compared page by page with
   Word (local only: Word output can't be committed; keep a manifest and our own renders).
2. **Preserve what we can't render**: remaining ink forms and unsupported graphics survive a round trip
   (keep the parts and the run). Charts, SmartArt and OLE objects do; drawing-level and direct run-level native ink now keep their InkML and optional picture fallback.
3. Move tracking (`w:moveFrom`/`w:moveTo`) read and written (formatting revisions: #41; content controls: #381).
4. Encrypted `.docx` opens with a password.

## Imported TOC result preservation

Original synthetic TOCs without TOC paragraph styles lose their outer result range on main
and. Main also flattens a nested page field in a single-paragraph result. Imported TOCs
now use the existing range-field markers to retain the actual result boundaries, nested
page-reference fields, formatting, links and locks through edited saves.

The public [complex-field contract](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.fieldchar?view=openxml-3.0.1)
defines begin/separate/end delimiters and permits nested fields. Paragraph styles do not define
those boundaries. A complete range is converted to the engine's styled TOC representation only
when that writer can reproduce its exact extent; partial or custom-styled ranges stay explicit.

Focused original regressions cover single/multiple paragraphs, partial ranges, adjacent styled
text, multiple/simple fields, table cells, section breaks, missing ends and bounded nesting.
The existing styled TOC write/read path remains supported. Update Table and Update Fields refresh
unlocked top-level body TOC ranges in place through the engine's generator; one undo restores
the imported range. Locked, nested and table-cell ranges remain preserved without regeneration.
Preservation is separate from field evaluation. Native Word reopening and
refresh, full schema validation and company documents remain untested. Synthetic checks do not
raise readiness estimates. No Word-derived files are fixtures.

## Settings preservation

A save used to regenerate `settings.xml` from the model alone, so every setting the model doesn't
hold was dropped without a warning (on 18 real-world Word documents: compatibility settings in 18
of 18; the privacy options are modelled since). Now the writer merges into the
file's original (`crates/docx/src/write/settings_merge.rs`): the original root and every child
the model doesn't own stay byte for byte; owned children follow the model, in CT_Settings order;
in `w:compat` only `compatibilityMode` is replaced. Kept children that point at a relationship keep
it: the settings part's relationships are carried under the same ids, external targets as they
are and internal ones with their parts, so a mail merge main document's `w:mailMerge` (main
document type, data source and header source, query, field mapping, recipient data) survives a
save byte for byte though Etch has no mail merge; a child naming an id the file didn't relate
is dropped rather than left dangling. Files Etch wrote itself keep nothing extra. Tests:
`crates/docx/tests/settings_merge.rs`, `crates/engine/tests/merge_fields.rs`.

## Unmodelled-part preservation

Parts the package or the main document relate to that Etch neither models nor writes (web
settings, styles-with-effects, add-in task panes, people, the thumbnail, future parts) are
carried verbatim with their relationships and content types. The glossary document is carried the
same way while its building blocks are as read; once they change it is written from the model. Relationship types the writer
produces, and any the document's markup refers to by id, are not (`HANDLED_RELS` in
`crates/docx/src/read/embed.rs`), so nothing is written twice. `app.xml` keeps Template, Manager,
Company, HyperlinkBase and the link/sharing flags; counts (pages, lines, characters, editing
time) and the producing application's version are not carried, and Manager and Company are
dropped when the file asks to remove personal information on save. Headers, footers, the notes parts and the comments part keep their own such relationships too (`H<part id>`, `F`, `E`, `C` owners in the manifest). Not yet: unknown elements and
attributes inside stories and style or list definitions; a regenerated theme. Tests:
`crates/docx/tests/passthrough.rs`.

## Saving in a format that can't keep everything

Only formats whose round trip is proven by tests keep the whole document: Word's packages
(`.docx`, `.docm`, `.dotx`, `.dotm`), Word XML (`.xml`, Flat OPC, written by the same writer and
tested equal to `.docx`) and Etch's JSON (`wordcraft_engine::io::keeps_everything`). ODT and
RTF keep notes, comments, headers and footers, tracked changes, text boxes and sections, but not
comment threads, moves (an RTF also not a note's own mark), content controls, shapes or
equations, so they still ask; every other format goes through a small flow model that has none
of these. What each format loses is measured, not assumed: the fidelity harness
(`crates/engine/tests/format_fidelity.rs`) saves a corpus of one synthetic document per feature
in DOCX, JSON, ODT, RTF, HTML and Markdown (directly, via DOCX, and saved twice), pins what each
still loses, and fails when `io::lossy_features` names something kept or misses something lost.

- **The first Save over such a file in a session asks first**, as Word does: a prompt names what
  the format would lose of this document (comments, footnotes, endnotes, headers and footers,
  tracked changes, text boxes, equations, content controls, shapes and charts; nested tables for
  Markdown and text; pictures for Markdown and text; for ODT and RTF only comment replies, moves,
  RTF note marks, equations, content controls and drawings; and formatting
  the format has no way to write (Markdown and text: underline, superscript and subscript,
  colours, highlights, fonts and sizes, alignment, right-to-left paragraphs, spacing and indents,
  tabs, page breaks, column widths and cell shading; every text format: position tabs, hidden
  separators and smart tags), fields the format can't keep (all of them for HTML, Markdown and
  text; for ODT and RTF those outside their vocabularies, `odt::KEPT_FIELDS` and
  `rtf::SIMPLE_FIELDS`), merged cells (Markdown, text), sections (HTML, Markdown, text), page setup
  and document properties (Markdown, text); `io::lossy_features`) and offers Keep format (saves,
  and the document counts as saved, as Word's choice does; later saves of that document and file
  don't ask again, unless the document has since gained something more the format can't keep,
  which is asked about too) or Save as .docx… (Save As with a Word document suggested). The "Save
  changes?" prompt's Save asks the same, then carries on. Save As to such a format doesn't ask:
  the person picked it.
- **A macro project is kept only by `.docm`, `.dotm` and Etch's JSON** (`io::drops_macros`):
  a save of a document holding one (read from a `.docm`/`.dotm`) in any other format, a `.docx`
  or `.dotx` included, names `macros` ("Macros") in what it loses. Save As, File › Export and a
  Save Copy to such a file ask first, as Word warns before saving a macro-free document (Keep
  format saves without the macros; the other button goes back to Save As with `.docm`, or `.dotm`
  for a template, suggested); the new `.docx` becomes the document's file and later saves of it
  don't ask again; the open document keeps the project, so a later Save As `.docm` writes it back.
  AutoSave doesn't write such a file ("AutoSave is off: … can't keep this document's macros"),
  scripts get `lossy: ["macros"]`, the CLI warns on stderr, and a browser download says so on the
  status bar. The `.docm` on disk keeps its macros. Measured by the harness's `macros` row
  (`format_fidelity.rs`) and `tests_save_safety::a_save_that_leaves_out_the_macro_project_names_it`,
  `save_as_a_macro_free_word_document_says_so_and_keeps_the_project_in_the_open_document`,
  `tests_save_format::save_as_a_macro_free_word_document_asks_first`,
  `every_save_as_that_would_drop_the_macros_asks_first`, `a_browser_download_without_the_macros_says_so`
  and `etch-cli` `a_conversion_that_leaves_out_the_macros_says_so`.
- **A Word 2003 XML Document is such a format**, though its `.xml` name is a Word XML Document's:
  a save over one (or `format: "wordml2003"`) asks and reports what the 2003 vocabulary can't hold
  (text boxes, equations, content controls, drawings, comment replies, a note's own mark, moves
  and formatting changes, the even pages' headers; `io::lossy_features_with`, measured by the
  harness's `wordml2003` column), and AutoSave doesn't write it (it wrote a Word XML Document over
  it before, changing its format unasked).
- **AutoSave never writes such a file**; its switch says to save as .docx.
- **Scripts are never asked** (CLI, the control channel): `file.save` saves and its result
  has `"lossy": [...]`, the features lost (empty when the document uses none of them), whenever
  the format can't keep everything (`docs/control-protocol.md`). `etch-cli convert`, `run
  --save` and `zotero --save` say on stderr what the file is without (a PDF, a picture of the
  pages, isn't warned about).
- **One set of limits for the editor and every reader** (`wordcraft_doc::limits`): 250,000 paragraphs, 750,000 runs, 25,000 secondary stories (headers, footers, notes,
  comments and text boxes), 10,000 styles, lists and bibliography sources, 5,000 sections,
  100,000 revisions, 5,000 pictures, 256 MB of pictures and embedded files, and 256 MB of saved
  text and formatting (an upper bound of what the Word writer emits, checked against it for every
  feature of the fidelity corpus; Word XML, Etch's JSON and recovery copies are bounded by
  it too). Every story is counted, and only what an edit changes is counted again.
  - **No edit takes a document past any of them** (typing, a paste, Enter, an inserted picture
    or table, Replace All, Compare, a field, a Zotero citation): it is refused with the limit and
    what to do in the status bar, and the document and its undo history are as they were. Undo
    and Redo are exempt; a document opened over a limit stays editable as long as it doesn't
    grow (`tests_limits::every_limit_holds_edits_up_to_it_and_refuses_one_past`).
  - **No reader drops what is over a limit**: DOCX, Word XML, Word 2003 XML, `.doc`, ODT, RTF,
    HTML, Markdown, LaTeX and plain text refuse a file past one with a `limit exceeded` error naming it
    (they kept the first 10,000 styles or lists, or the first 50,000 notes and comments, without
    a word, and a save then destroyed the rest), and opening checks the counts and the tables'
    nesting, rows and cells whatever the format.
  - **What Etch saves within the limits opens again**: the readers' byte limits follow from
    the saved-size limit (an XML part 320 MB, a package's parts 576 MB), and the readers count as
    the editor does (a drop cap written as two paragraphs counts one, the note separators the
    writer adds aren't the document's), so a document at the limits saves as DOCX, Word XML and
    Etch JSON and opens again the same (`tests_limits`; at the real limits, ignored).
- **A format Etch can't write** (Word 97-2003 `.doc`/`.dot`): the person's Save, and the
  "Save changes?" prompt's, go to Save As with a `.docx` suggested; a script's `file.save` is an
  error that names `file.saveAs` with the `.docx` path.

The fidelity harness also saves every corpus document twice and after a reopen, byte for byte
(`every_format_saves_the_same_bytes_twice_and_after_a_reopen`): nothing in a file depends on the
clock, and a second save changes nothing (known differences are listed with their causes).
Hostile input: `crates/formats/tests/mutation_fuzz.rs` mutates synthetic RTF, ODT (package and
flat), HTML and Markdown seeds (bit flips, cuts, deep nesting, huge counts, bad encodings,
unbalanced groups, deflate bombs): every mutant opens or is refused in bounded time, and what
opens saves and opens again (`FUZZ_ROUNDS=n` runs longer).

Tests: `crates/engine/src/tests_limits.rs` and `crates/docx/tests/shared_limits.rs` (the shared
limits: edits at and one past each, the size estimate against the writers, files one past each
reader cap), `crates/engine/src/io/fidelity.rs` (classification, reported features),
`crates/ui-egui/src/tests_save_format.rs` (the prompt for an `.odt` with a footnote, Keep format,
Save as .docx…, AutoSave not writing it, scripts' `lossy`, the quit prompt, `.doc`, a Word 2003
XML file, asking again when more would be lost), `crates/engine/src/tests_save_safety.rs` (saves,
exports and recovery copies with a fault injected at every durable step; the paragraph cap; Word
2003 XML), `apps/wordcraft-cli` (`a_lossy_save_says_what_the_file_is_without`).

## Saving legacy Word imports

Word 97–2003 `.doc` and `.dot` remain import-only. A user Save without an explicit destination opens the existing Save As flow suggesting DOCX, including before Close. The original stays unchanged. Cancelling retains the draft, revision and path; a failed write keeps the draft open, and successful DOCX save/reopen retains the edited text. Uppercase extensions follow the same route. Scripts and explicitly supplied legacy destinations still receive an unsupported-format error and never open a dialog. Late Save As answers are rejected before writing if automation has replaced the document.

Original binary fixtures and actual WordApp/Session file I/O cover Save, toolbar dispatch, a Mod+S input event, cancel, failure, retry, close continuation and repeated DOCX saves. The picker service is controlled in these tests; a native Windows picker and broad legacy-document fidelity remain unqualified.

## Cached field result formatting

Imported text fields use the first nonempty cached result run's formatting on their paragraph span, including character styles. Empty results retain begin-marker formatting. Synthetic fixtures cover simple and complex fields, default inheritance and repeated saves. Mixed-format results remain represented by one span; field refresh policy is unchanged.
